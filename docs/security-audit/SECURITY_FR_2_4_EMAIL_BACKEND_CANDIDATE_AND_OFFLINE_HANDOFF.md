## Implemented source candidate

Actual executable SQL is saved under supabase/candidates/security_fr_2_4_email_verification_backend.sql, deliberately outside ordered migrations/schema integration and without changing the current application's data-access policies. Server crypto module supabase/functions/_shared/email-verification-crypto.mjs is executable portable WebCrypto source for cryptographic six-digit generation, bound code HMACs and independent256-bit remembered-device credentials/digests. No mocked approval algorithm is substituted for these SQL functions in local verification.

Five private tables hold account security versions, rolling send-attempt reservations, challenges, devices and session proofs. Every table enables/forces RLS and grants no direct schema/table access to anon/authenticated/service_role. Eight public service-only SECURITY DEFINER RPCs have a pinned pg_catalog search_path: begin_challenge,set_delivery,challenge_context,verify_challenge,restore_device,revoke_device,revoke_all,session_status with the email_gate_ prefix. Six private helpers have all API EXECUTE grants revoked. Only postgres with privileged SQL capability and the explicit offline-review acknowledgement can create the candidate namespace; repeated/colliding installation refuses rather than replacing existing objects. This guard is a source-review barrier, not proof of hosted project selection or readiness.

The database requires a confirmed active Auth user, a matching existing auth.sessions row and valid optional not_after timebox. The future trusted service adapter must first validate the real bearer through Auth and derive the actor/session values. Supplying UUID arguments to a service-only SQL function is not itself genuine Auth verification. Anonymous and ordinary roles cannot gain service privilege by changing JWT claim settings.

Codes are HMAC-bound to actor/session/challenge/key version; plaintext codes and pepper never enter SQL storage. The private keyed digest comparison reads every digest byte. Challenges expire after600seconds of database time; failed attempts commit and lock after5. Pending/failed delivery cannot verify; resend supersedes pending codes on the same actor/session, and stale callbacks/replays cannot revive them. Bounded service-only context returns key version/remember flag/expiry so the future sender/verifier can rotate server keys without exposing stored code MACs. A60-second cooldown and5 send-attempt reservations in a rolling hour are serialized by account row locks. These reservations survive Auth logout and include failed mail attempts; they are not evidence that an email was sent.

Successful verification optionally creates a604800-second approval for a random device credential and a separate session proof. Restoring that credential to a fresh same-account session preserves the original approval expiry. Other accounts/devices require their own code. Approval expiry alone does not invalidate an already verified active session; the next new sign-in requires a code, matching the selected day7 trigger. Auth session deletion cascades its challenge/proof rows while device approval persists until expiry or revocation. Forget-device and revoke-all require existing verified session proof; credential/email/ban changes and profile suspension invalidate account proofs/devices through two newly added callbacks. These callbacks are candidate additions; original callbacks/bodies/grants/policies are retained. Source model retains the pre-existing workspace-owner Auth-deletion restriction; full account-deletion lifecycle is not claimed accepted.
