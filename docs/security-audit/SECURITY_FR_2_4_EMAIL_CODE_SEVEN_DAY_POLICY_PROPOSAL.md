## Requested experience and scope question

Owner prefers email-delivered codes over an authenticator app, without requiring a code on every login; after7days, a subsequent sign-in should require a new code. The authenticator work so far was for isolated platform Admin/recovery logins, not a blanket requirement on Personal/Family/Business customer users. The repeated terminal sign-ins were audit/session checks, not a product decision to prompt on every app opening. A Business workspace Owner or business_admin is distinct from platform staff managing customer accounts.

Proposed default keeps email/password login and adds an email verification challenge with an explicit Remember this device for7days choice. Scope needs one owner clarification: ordinary customer accounts only, or platform Admin/staff too? Recommended split: convenient email verification/remembered device for customer accounts, retain stronger MFA for platform staff. If owner chooses email for platform staff as well, prepare a separate security/authorization redesign and record its weaker mailbox-dependent proof honestly; do not silently mark AAL2/F08/F15 satisfied or remove current guards to make the old candidate pass.

## Concrete proposed behavior for review

1. Correct password first. A new/untrusted browser or app installation receives a short-lived one-use email code. Successful verification may approve that specific account/device for7full days. Shared devices can leave the remember option off.
2. Within those7days, later password sign-ins on the same approved device need no new email code. Signing out ends that Auth session; keeping device approval until its fixed expiry is a separate explicit product choice. It is not a still-valid login session.
3. Seven days runs from the last successful email-code verification, not the most recent password login; routine use does not extend it indefinitely. On the next sign-in after expiry, require a new code. An already active session is not automatically logged out or emailed at day7 under the owner's stated trigger. Sensitive actions can separately require recent proof.
4. Another browser/device, clearing the approval credential, password reset/change, email change, device revocation or a security-risk event can require a fresh code sooner. Provide Forget this device and revoke-all-device capability. Approval on one account/device cannot suppress another account's check.
5. Proposed challenge limits: approximately10-minute code lifetime, one use, bounded failed attempts and resend cooldown/rate limits. Seven days is device approval, never the lifetime of a single code. Exact challenge parameters remain review defaults, not adopted live settings. Provider failure must leave the login pending with retry/recovery handling; do not grant access because email is unavailable.

## Architecture and acceptance requirements before implementation

Supabase email OTP is a conventional sign-in method at aal1; it is not an Auth MFA factor that automatically upgrades a password session to aal2. Current reviewed platform assurance code calls admin_mfa_status and requires active staff, authorization and a verified factor; the frozen MFA SQL candidate is still uninstalled with no verified super operator in previous metadata. A standalone email OTP login or a visible email screen cannot meet those gates. Never spoof aal2, alter only UI conditions or skip RLS/RPC/Edge/Storage checks.

A password-plus-email remembered-device scheme requires server-enforced proof bound to actor and sign-in attempt/session, and a protected random device credential with server expiry and revocation. A browser timestamp/localStorage Boolean or a global per-user last-verified timestamp is insufficient: a new device/direct API caller could otherwise bypass the challenge. Enforce across direct data/RPC/Storage/Edge paths, including refreshed sessions, account switches and revocation. Do not extend access JWT lifetime to7days to simulate trust. Web/PWA cookie/gateway design and native secure-storage/revocation design need a concrete implementation plan; the static direct-upload deployment does not supply a trusted-device backend by itself.

Existing ordinary password sign-in can already produce a usable Auth session; showing an email modal afterward alone would not deny direct APIs. Determine whether built-in Auth OTP or a separate challenge service fits the approved scope; any built-in signInWithOtp use must prevent unintended user creation. Shared Magic Link/OTP email templates and OTP expiry can also affect confirmation/recovery/email-change/invitation flows, so do not blindly change the global email template/expiry. Preserve Stage3 Auth and Stage6 invitation/provider/linking contracts and retest them. SMTP/sender delivery, ownership, inbox spam/retry behavior and real controlled mail receipt are still acceptance work, not implied by this preference.

Security tradeoff: mailbox compromise may expose both password recovery and email codes. Email verification can add protection to password-only login but is not equivalent to an independent authenticator factor or phishing-resistant authentication. No NIST conformity or store-policy requirement is claimed. Stronger protection remains recommended for platform staff; owner scope decision governs the next concrete plan.
