## Actual source additions

The gateway module exports its actual default Worker-style fetch entrypoint plus factories used by source tests. It is not copied into current static output, deployed as _worker.js or installed into existing clients. No existing application functions/policies/roles/guards or build exports are modified.

All six authentication routes are JSON POSTs under /api/email-verification/: begin,verify,restore,status,forget,revoke-all. They require the exact staging origin,custom x-mushavo-csrf email-v1 header and same-origin Fetch Metadata when supplied; there is no permissive CORS response. Query-bearing,unknown,GET,oversized and extra-authority-field requests are denied. Dynamic responses have no-store,nosniff,referrer/CSP restrictions and generic errors. Upstream calls are fixed HTTPS destinations with redirects disabled,8second deadlines and bounded JSON streams. Static fallback forwards GET/HEAD through ASSETS while stripping bearer/cookie headers and retaining asset response/security headers.

The adapter parses bounded JWT claims only to reject malformed requests; it never authorizes from decoding alone. It presents the exact same bearer to staging Auth /auth/v1/user with the publishable key, then compares returned confirmed nonanonymous user identity to sub and binds the signed session_id,issuer,audience,role and expiry. The actual SQL independently requires a matching active Auth session/profile. Browser email,user-ID,device credential and expiry inputs are rejected. Service-key calls are restricted to the eight E2RPC names and use server-only runtime credentials. Local Auth responses are synthetic; provider signature checks and real hosted key ownership are not established by these tests.

The code is cryptographically generated and HMAC-bound by the existing actual crypto module. Only the HMAC enters SQL; plaintext goes to the mail adapter. The mail recipient is the Auth-returned address and must additionally be in a private controlled test allowlist of1to10single inboxes. Only provider success marks delivery ready; failed/token-error/redirect/error-body cases mark failure and cannot return a ready challenge. Late delivery acknowledgement refusal remains unavailable. Code verification uses the challenge's stored key version to support pepper rotation, creates a device credential only when remember is selected and exposes it only in a Secure,HttpOnly,SameSite=Strict,Path=/,__Host- cookie named per account. JSON never returns a raw code,device credential,email or user identifier. A same-account restore never renews the cookie or database deadline; an already verified open session remains valid without attempting restore after day7. Forget/revoke operations call the proof-protected SQL routines before clearing the corresponding account cookie.
