## Wrapper defect and scope of the correction

The original wrapper leaves its checkpoint at SOURCE_TOOLS_AND_PACKAGE_PREPARATION until immediately before opening the ZIP. That label also covers JSON receipt parsing,contract/public-set checks and the non-configuration manifest count. It does not establish that the Node process itself failed. The API diagnostic now proves successful preparation in the Windows temporary-folder context.

Review identifies a Windows PowerShell 5.1 compatibility defect in the original manifest expression: an array of rows is sent by ConvertFrom-Json as one pipeline object,so wrapping that pipeline directly with @() can count one containing array rather than the 43 manifest rows. The new wrapper first assigns the parsed value to a variable,then explicitly enumerates it with @($ParsedManifest). This follows the behavior and workaround discussed in the official PowerShell issue #3424. The original failure's exact thrown exception was hidden,so a causal assertion that it was MANIFEST_COUNT_REVIEW_REQUIRED remains unproven until actual Windows evidence. The retry includes a harmless 43-number JSON probe reporting both the legacy expression count and corrected count. It requires the corrected count to equal 43. No artifact count or content check is relaxed.

The source correction is in a separate retry wrapper;the original 57-input preparer,original wrapper,source contract and frozen source manifest remain byte-identical. Existing receipts and original source pins remain valid and historical. The new wrapper uses a new ordinary local TEMP review folder,the location type already exercised by the successful owner diagnostic. This removes a dependency on Desktop known-folder resolution without asserting that Desktop redirection caused the prior failure.
